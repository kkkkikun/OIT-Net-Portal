# 反馈通道改为飞书直发 —— 设计说明

## 设计目标

把「作者机器上常驻一个服务」换成「云端常驻服务」，同时不把同学的反馈内容交给
除飞书之外的任何第三方。

## 背景：为什么自托管在校园网场景不合适

上一版的收集端要求作者的机器常驻且网络可达。校园网环境下这是硬约束：

- 机器关机 / 休眠 / 换网络 → 同学提交静默失败；
- 作者要随时看反馈 → 那台机器必须一直开着；
- 校园网常有 IP 变动，同学手机上的地址要跟着改。

飞书是常驻服务，作者不占机器；代价是提交目标从「自建服务」变成「第三方 webhook」。

## 通道形态：两种飞书 webhook，请求体不同

飞书有两种都能「外部 POST 写进去」的通道，官方文档里请求体形状不一样：

| | 群自定义机器人 | 多维表格自动化 webhook |
|---|---|---|
| 地址 | `https://open.feishu.cn/open-apis/bot/v2/hook/<id>` | 自动化流程「接收到 webhook 时」节点给出的地址 |
| 请求体 | `{"msg_type":"text","content":{"text":"..."}}` | 扁平 JSON，键名对应表格列名 |
| 成功判定 | HTTP 200 且 `code == 0` | HTTP 200 且 `code == 0` |
| 配置成本 | 群里加个机器人即可 | 建表 → 建自动化 → 映射字段 |
| 集中处理 | 群聊消息流 | 表格：可筛选 / 排序 / 标状态 |

**实现按地址形态自动区分**：URL 含 `/open-apis/bot/` 走群机器人形态，否则走扁平 JSON 形态。
这样用户在 App 里只填一个地址，不用选类型；填错了会在飞书侧报错而不是静默丢数据。

## 为什么主推多维表格

用户的诉求是「最后集中处理」。表格天然是行式结构：

- 每条反馈一行，字段固定（内容 / 分类 / 诊断摘要 / App 版本 / 时间）；
- 可以按「分类」筛选、按「时间」排序、加一列「状态」标已处理；
- 手机上飞书 App 直接能看，不用开电脑。

群机器人是零配置备选：适合「反馈量不大、就想在群里看一眼」的场景。

## 关键取舍：webhook 地址会进 APK

这是本变更最重要的安全取舍，必须讲清楚：

- 飞书 webhook 地址本身就是**写入凭据**。谁拿到它，谁就能往你的表/群写内容。
- App 要零配置直发，这个地址就必须在 APK 里 → **可被提取**（反编译 APK 即可）。
- 缓解手段在飞书侧，而且**必须开**：
  - 群机器人 → 「签名校验」（HMAC-SHA256）或「自定义关键词」；
  - 多维表格 → 「凭证校验」（Bearer token）。
- 因此 App 必须**能携带凭证**。这看起来和「不把凭据放进 APK」矛盾，但两者风险不同：
  - 只有地址泄露 → 开了校验就完全无效；
  - 地址和凭证都在 APK → 提取者需要反编译 APK，门槛高一个量级，且拿到的权限
    仅限「写这一个表/群」。
- 对比上一版的取舍：GitHub Issues 方案要把 token 塞进 APK，token 能改仓库代码、能提 PR、
  能读私有内容，**危害远大于**「只能往一张表写一行文字」。
- 结论：飞书直发可接受，但**飞书侧的校验必须开**，且文档要写清楚。

## 载荷对齐表格列

多维表格的列名就是 webhook 请求体的键名，所以载荷字段名要稳定且能直接当列名用：

| 载荷字段 | 表格列 | 说明 |
|---|---|---|
| `content` | 内容 | 同学填的正文 |
| `category_label` | 分类 | 中文（建议 / 问题 / 其他），可直接做单选列 |
| `diagnostics` | 诊断摘要 | 可空 |
| `app_version` | App 版本 | 定位问题版本 |
| `submitted_at` | 时间 | ISO 8601 |

`category`（英文机器值）保留在载荷里，供自托管收集端与后续程序化处理使用；
`category_label` 是给人看的，也是表格单选列要的。

## 失败判定：飞书返回 code != 0 也是失败

飞书群机器人即使 HTTP 200，也可能返回 `{"code": 19021, "msg": "关键词不匹配"}`。
只看 HTTP 状态码会把失败当成功 → 同学以为提交了，其实没进表。

因此提交层必须检查响应体的 `code` 字段。

## 保留自托管

自托管收集端**不删**：它在两种场景下仍然更合适——

- 需要**先审后收**（不希望同学的反馈直接出现在公开表里）；
- 需要**完全离线**（表格在飞书、反馈不出本机）。

App 里的地址是运行时配置，切回自托管只要改地址，不用重新打包。

## 方案比较（为什么不选其他）

1. **飞书开放平台 API 写入**（app_id/app_secret 换 token）：要建企业自建应用、申请权限，
   而且 app_secret 进 APK 的危害比 webhook 更大。**不采纳**。
2. **Google Form / 问卷星**：同学要跳出 App（正是要避免的），且收集仍需人工导出。**不采纳**。
3. **Webhook.site / Server酱**：数据经第三方中转，且临时性/额度受限。**不采纳**。
4. **飞书直发（采用）**：常驻云服务、同学零门槛、表格可集中处理；代价是地址进 APK，
   用飞书侧校验缓解。

## 依赖与边界

- 无新增第三方依赖：签名用标准库 `hmac`/`hashlib`/`base64`/`time`。
- Android 侧不新增权限（提交用既有 `INTERNET`）。
- 不改 `network_security_config.xml`：飞书是 HTTPS，不受明文策略影响。
