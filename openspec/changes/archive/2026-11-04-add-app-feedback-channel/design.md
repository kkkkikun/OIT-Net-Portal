# App 内嵌快速反馈通道 —— 设计说明

## 设计目标

「快」是唯一的设计目标，分三层：

1. **入口快**：同学在设置页底部一眼看到「意见反馈」，一次点击进入表单。
2. **填写快**：三个字段，无账号、无附件、无评分；诊断摘要是一个开关（默认关）。
3. **收集快**：作者不需要逐条点开收集端网页去捞，反馈直接落本机文件，`list` / `export` 一条命令出清单。

## 为什么是「App 内原生表单」而不是问卷链接

用户提出的关键疑问是「能内嵌到 app 里面吗，用问卷会不会需要再点开一个链接」。

- **问卷链接方案**：同学点「意见反馈」→ 跳出 App → 打开浏览器 → 加载第三方问卷页 → 填 → 提交。
  中途跳浏览器是体验断点，且大多数问卷平台没有免登录的程序化提交接口，收集端仍是人工导出。
- **内嵌 WebView 方案**：视觉上在 App 内，但本质仍是加载第三方网页；受平台域名白名单、加载失败、体验割裂影响，
  且仍需同学自己填全部字段，诊断摘要这类上下文也塞不进去。
- **原生表单方案（采用）**：表单是 App 自己的 Compose UI，字段与 App 状态打通（诊断摘要可一键附带），
  提交走 App 自己的 Python 核心通道，全程不跳 App、不开浏览器。

## 架构

```
同学 App（Android）
  设置页 → 意见反馈卡片 → FeedbackForm（Compose 原生表单）
      ↓ PortalViewModel.submitFeedback()
  FeedbackBridge（core 契约）
      ↓ Chaquopy
  oit_portal/feedback.py → build_feedback_payload() → POST JSON
      ↓
  作者机器：oit-portal feedback serve（HTTP 收集端）
      ↓
  1) JSONL 追加落盘（权威副本，永远有）
  2) 可选：转发飞书多维表格 webhook（有配置才发，失败不阻塞落盘）
```

反向（作者集中处理）：

```
oit-portal feedback list      # 终端列出
oit-portal feedback export    # 导出 Markdown 清单
```

## 关键设计决策

### 1. 载荷 schema 与脱敏边界

载荷固定五个字段，字段名与类型对作者稳定：

| 字段 | 类型 | 说明 |
|------|------|------|
| `category` | string | `suggestion` / `issue` / `other` |
| `content` | string | 同学填写的正文（必填） |
| `with_diagnostics` | bool | 是否附带诊断摘要 |
| `diagnostics` | string | 脱敏摘要（可为 null） |
| `app_version` | string | App 版本，便于定位问题版本 |

**诊断摘要只取 App 已有的脱敏会话事件**，不新增采集面。构造摘要时逐条过滤：
丢掉含疑似账号、密码、Cookie、完整 URL 的行，只保留状态类事件文本。

作者侧定位问题靠「App 版本 + 连接状态 + 状态类事件」这三样，不靠用户口述机型和运营商。

### 2. 收集端为什么是 Python 自带而不是第三方表单

- 零第三方账号：作者不需要注册任何平台，也就不存在「平台倒闭/改规则/要付费」的风险。
- 反馈不外流：数据落在作者自己机器上，符合项目一贯的安全与隐私约束。
- 可选飞书：需要「手机上随时看」的便利时才配置 webhook，不配置也完全可用。

收集端用标准库 `http.server`，不引入新依赖。

### 3. 落盘优先、转发其次

飞书转发是**可选增强**，不是依赖。写入顺序固定为「先落盘、后转发」：
转发失败只记日志，不影响反馈是否被收集到。反过来做会出现「飞书抖动 → 反馈丢了」。

### 4. 监听地址默认回环

`feedback serve` 默认 `--host 127.0.0.1`。要让同网段同学提交需显式 `--host 0.0.0.0`。
这是显式取舍：默认不把一个无鉴权的写接口暴露到网络上。

收集端**不做鉴权**，因此它只适合可信校园网内网使用；这一点在命令输出与文档里都要写清楚。

### 5. App 侧收集端地址可配置

收集端地址写在 App 的本机设置里（`SharedPreferences`，非敏感），作者分发时通过一个可配置的默认值填好；
同学若换网络可自行改成新地址。不写死 IP，避免作者换网络就要重新打包。

### 6. 复用既有 HTTP 通道

提交走 `network.create_session()`（`trust_env = False`），不新建网络栈、不引入 OkHttp。

## 方案比较（收集端）

1. **第三方问卷平台**：无需自建，但同学要跳浏览器，且收集仍需人工导出，无免登录写入接口。
2. **GitHub Issues API**：需要往 APK 里塞 token（同学可提取），且反馈内容公开。不采纳。
3. **飞书多维表格 webhook 直写**：App 直接发飞书，但 App 里要内置 webhook 地址，且没有本机权威副本。
4. **自托管 + 可选转发（采用）**：本机永远是权威副本，飞书只是可选镜像。

## 依赖与边界

- 无新增第三方依赖（HTTP 服务用标准库 `http.server`，HTTP 客户端用既有 `requests`）。
- Android 侧不新增 Compose 依赖，不新增 Android 权限（提交用既有 `INTERNET`）。
- `cleartextTrafficPermitted` 默认仍为 false；作者若用 http:// 内网地址提交，需在
  `network_security_config.xml` 显式放行该主机——这是既有安全策略，本变更不放松它。
